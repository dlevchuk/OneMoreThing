# Дошка контрактів

Публічний список бажань на GitHub Pages. Головна сторінка — вступний екран; кнопка «Зайти в матрицю» відкриває `board.html`, де відвідувачі можуть шукати й фільтрувати записи, переглядати досьє та переходити за посиланнями на товари. Сайт статичний: окремої адмінки й кнопки редагування на сторінці немає.

## Структура репозиторію

```
/
├─ index.html, board.html     сторінки (лишаються в корені, щоб URL не змінились)
├─ assets/                    favicon.svg, apple-touch-icon.png, og.png
├─ css/                       style.css, theme.css, booking.css
├─ js/                        rain.js, transition.js, birthday.js, app.js, booking.js
│                             (+ supabase-config.js — генерується в CI, у git не комітиться)
├─ data/wishes.json           список бажань
├─ supabase/                  schema.sql, config.example.js
└─ .github/workflows/         deploy.yml
```

## Як оновити список

Власник репозиторію відкриває `data/wishes.json` у GitHub, додає або редагує запис і комітить зміну до гілки, з якої публікується GitHub Pages. Нові картки з’являться після завершення публікації.

Після зміни ID або додавання/видалення подарунків запусти `npm run catalog`, закоміть оновлений `supabase/schema.sql` і виконай його в SQL Editor потрібного Supabase-проєкту. Сервер дозволяє бронювання лише активних ID з цього каталогу. Старі бронювання зберігаються; неактивні та сторонні ID не займають ліміт активних подарунків. `npm test` перевіряє відповідність каталогу JSON.

Оновлення захисту на вже налаштованому сайті: повторно виконай весь `supabase/schema.sql`. Воно зберігає бронювання й коди скасування, синхронізує каталог та замінює RPC. Нові коди мають щонайменше 12 символів; старі чотиризначні коди залишаються придатними для скасування.

Приклад картки:

```json
{
  "id": "steam-deck",
  "title": "Steam Deck",
  "description": "Портативна ігрова консоль",
  "image": "https://example.com/steam-deck.jpg",
  "originalUrl": "https://example.com/product",
  "localUrl": "https://hotline.ua/example-product/",
  "priority": "want"
}
```

Кожна картка має мати унікальний `id`, назву `title`, пряме посилання на зображення `image` і пріоритет `priority`. Додавай `originalUrl` для сайту виробника та `localUrl` для локального продавця; для пошуку локальної ціни спершу перевір Hotline. `description`, `originalUrl` і `localUrl` можна пропустити, якщо для них немає даних. Пріоритети в JSON: `want`, `nice`, `unsure`.

Публічні відвідувачі не можуть редагувати репозиторій через сайт. Доступ до змін визначають права GitHub на репозиторій і гілку публікації.

## Публікація

У GitHub відкрий **Settings → Pages** і вибери **Source → GitHub Actions**. Workflow `.github/workflows/deploy.yml` збирає `dist/` з `index.html`, `board.html`, `css/`, `js/`, `assets/` та `data/` і деплоїть його.

## Анімації та доступність

Дошка має анімований цифровий дощ, прокручуваний рядок і неонові ефекти. Анімації вимикаються або спрощуються, коли система запитує зменшення руху.

## Бронювання контрактів (Supabase)

Гості можуть закріплювати (бронювати) за собою контракти на подарунки, щоб інші відвідувачі бачили, що подарунок уже обрано, або перемикати фільтр «Тільки вільні».

### Як налаштувати Supabase без збереження ключів у репозиторії:

1. Зареєструйся на [supabase.com](https://supabase.com) і створи новий безкоштовний проект.
2. У меню зліва відкрий **SQL Editor**, створи новий запит («New query»), скопіюй вміст файлу `supabase/schema.sql` і натисни **Run**. Це створить:
   - таблицю `reservations`;
   - правила безпеки Row Level Security (RLS);
   - безпечну функцію скасування за кодом скасування;
   - Realtime-підписку для синхронізації в реальному часі без перезавантаження сторінки.
3. Перейди в **Project Settings → API** (або Data API) і скопіюй:
   - **Project URL**
   - **anon / public** API Key
4. Додай секрети у свій GitHub-репозиторій:
   - Відкрий репозиторій на GitHub → **Settings → Secrets and variables → Actions**.
   - Натисни **New repository secret** і створи:
     - `SUPABASE_URL` — встав свій Project URL.
     - `SUPABASE_ANON_KEY` — встав свій anon public key.
5. Увімкни деплой через Actions:
   - У GitHub відкрий **Settings → Pages**.
   - У полі **Build and deployment → Source** вибери **GitHub Actions**.
6. При кожному пуші до гілки `main` GitHub Action (`.github/workflows/deploy.yml`) автоматично підставить секрети у файл `js/supabase-config.js` під час збірки. У відкритому репозиторії ключів не буде!

#### Локальна розробка:
Для локального тестування скопіюй `supabase/config.example.js` у `js/supabase-config.js` (цей файл у `.gitignore` і не потрапить у git) і вкажи ключі там, або нічого не вказуй — тоді сайт автоматично працюватиме в локальному демо-режимі через `localStorage`.

## Вхід власника та виконані контракти

Відкрий `owner.html` (посилання «Вхід власника» внизу дошки), введи email і відкрий одноразове посилання з листа **в тому самому браузері**, де його замовив. Використовується Supabase Auth із PKCE. Пароль на сайті не вводиться. Після входу перейди до дошки: у досьє з’явиться кнопка «Позначити виконаним». Можна додати публічну подяку до 500 символів.

Виконані подарунки потрапляють до вкладки «Виконані», мають дату отримання й не допускають нових бронювань. «Повернути у вільні» очищає стан завершення, але не відновлює старі бронювання та коди. Зміна стану й закриття бронювання — одна транзакція, синхронізована з бронюваннями.

Налаштування нового Supabase-проєкту:

1. Виконай `supabase/schema.sql`.
2. Створи та підтвердь користувача власника через Authentication → Users.
3. Вимкни відкриту реєстрацію та anonymous sign-ins. Клієнт також використовує `shouldCreateUser: false`.
4. Адміністратор додає UUID створеного користувача в `private.site_owners.user_id`. Ця таблиця недоступна клієнтам; RLS і RPC перевіряють `auth.uid()`, а не email чи user metadata. Повторне застосування схеми не скидає власників і виконані стани.
5. У Auth → URL Configuration встанови Site URL і точну дозволену адресу `https://<твій-домен>/<шлях>/owner.html`. Для локальної розробки окремо дозволь `http://localhost:3000/owner.html` та `http://127.0.0.1:3000/owner.html`.

Стандартний поштовий сервіс Supabase має обмеження одержувачів і частоти. Для ширшого використання потрібен власний SMTP. Шаблон листа за замовчуванням надсилає посилання; код не обіцяємо, якщо шаблон не налаштований. Не додавай service-role ключ у браузерний конфіг.

`npm test` перевіряє Auth/PKCE, права UI, оновлення бронювань і каталог. SQL-сценарії `tests/sql-regression.sql` і `tests/owner-sql.sql` призначені лише для ізольованої БД з відповідними Auth fixtures, а не для запуску на production.

## Автоматичне додавання карток і моніторинг

### Додати товар одним посиланням

У GitHub відкрий **Actions → Add wishlist card from URL → Run workflow**,
встав URL сторінки товару та вибери пріоритет. Workflow:

1. Отримує назву, опис і фото з Product JSON-LD або Open Graph.
2. Створює стабільний ID, додає картку до `data/wishes.json` і генерує каталог.
3. Запускає тести, комітить зміни та окремо запускає публікацію Pages.

Повторне додавання того самого URL не створює дубль. GitHub має дозволяти
workflow запис у репозиторій; правила захищеної гілки також мають дозволяти push.
Нові ID для бронювань, як і раніше, потребують застосування згенерованого
`supabase/schema.sql` адміністратором за інструкцією вище. Імпортер не має
привілейованого ключа БД і сам її не оновлює.

Локальний варіант:

```bash
python3 -B scripts/add-wish.py 'https://shop.example/product' --preview
python3 -B scripts/add-wish.py 'https://shop.example/product' --priority want
```

`--preview` показує картку без запису. `--title` дозволяє задати назву вручну.
Якщо немає зображення, використовується favicon сайту. Сторінки з антиботом,
JavaScript-only метаданими або без надійних метаданих можуть потребувати ручної
картки; HTTP-помилки не перетворюються на вигаданий товар.

### Автоматичне створення моніторів

changedetection.io та таймер синхронізації працюють на Pi 4. Ansible, Telegram і таймер описані в README
репозиторію `homelab` (локальний каталог `raspberry`), розділ
«Changedetection.io and wishlist prices». Після одноразового налаштування API,
GitHub deploy key і `enable_wishlist_price_sync` кожен запуск таймера:

- читає каталог і сам створює відсутні watches з інтервалом 6 годин;
- знаходить свої watches за стабільними іменами, уникаючи дублів після перезапуску;
- повертає активні джерела з паузи; видалені/вимкнені/замінені джерела ставить
  на паузу зі збереженням історії; чужі watches не змінює;
- читає останній HTML snapshot і публікує ціну та наявність у `data/prices.json`;
- публікує короткі діагностичні стани в `data/monitoring-status.json`.

Якщо вже є один ручний watch з таким самим URL, він використовується без
переналаштування. Декілька watches для одного джерела потребують ручного вибору.

Моніторинг використовує **лише `originalUrl`**, тобто посилання «Джерело».
`localUrl`, старі перевизначення URL та `monitoring.url` не використовуються.
Без `originalUrl` товар пропускається. Старі автоматичні watches інших адрес
стають на паузу; їхні ціни не переносяться на нове джерело. Ручні watches
залишаються під керуванням власника. Нові імпортовані картки записують URL у
`originalUrl`. Для вибору правил джерела можна задати:

```json
"monitoring": {
  "profile": "manufacturer.example"
}
```

Без профілю ціна береться автоматично з єдиного Product/Offer JSON-LD
(також підтримується вкладений `priceSpecification`) або явних product-price
Open Graph/microdata. Суперечливі ціни не приймаються. Позначка
`valueAddedTaxIncluded: false` зберігається як `taxIncluded: false` і показується
біля ціни як «без ПДВ». Використовується ціна у валюті джерела (UAH, USD, EUR тощо).
Валюта зберігається й показується без перерахунку.
Декілька різних цін, відсутня/суперечлива валюта, AggregateOffer з діапазоном або відсутні дані
означають потребу перевірки. Мінімальна ціна агрегатора не видається за точну
ціну конкретного магазину. Для Hotline/OLX та інших нестандартних джерел можуть
знадобитися профілі, інше джерело або browser backend. Самостійний обхід антибота
та встановлення браузерного контейнера не реалізовані.

### Спільні правила магазинів

`config/shop-profiles.json` містить правила за hostname або іменем профілю.
Один профіль застосовується до всіх карток відповідного магазину:

```json
{
  "shop.example": {
    "store": "Назва магазину",
    "includeFilters": [".product-price", ".product-stock"],
    "priceRegex": "Ціна: ([0-9\\s,]+) грн",
    "decimalSeparator": ",",
    "inStockRegex": "^Є в наявності$",
    "outOfStockRegex": "^Немає в наявності$"
  }
}
```

Це приклад, а не готовий селектор магазину. `includeFilters` передаються
changedetection.io як CSS/XPath; оновлення профілю оновлює ці фільтри у власних
watches. Порожній список очищає фільтри. Без `priceRegex` використовується JSON-LD.
Для regex-профілю задавай `currency` (наприклад, `USD`); за замовчуванням UAH.
З `priceRegex` читається текстовий snapshot: перша група містить число,
регулярний вираз має збігтися рівно один раз. Використовуються Python regex,
multiline та пошук без урахування регістру. `decimalSeparator` — `,` або `.`;
інший символ вважається роздільником тисяч. Суперечливі ознаки наявності дають
стан «невідомо».

`config/price-watches.json` зберігає індивідуальні винятки за ID подарунка.
Старі правила з `watchId` підтримуються; такі watches вважаються ручними,
і скрипт їх не переналаштовує. Для повної автоматизації UUID вручну не потрібен.

### Актуальність, сповіщення та обслуговування

Картка показує останню відому ціну, магазин і дату перевірки. При помилці
попереднє значення і дата зберігаються з `checkFailed: true`. Дані старші за
24 години або позначені помилкою потребують перевірки; наявність не обіцяємо.
Без спостереження дошка працює як раніше. Новий watch спочатку має отримати
перший успішний snapshot; ціна може з'явитися під час наступної синхронізації.
Звіт розрізняє `ok`, `disabled`, `pending`, `fetch_error`, `filter_error`,
`paused`, `price_range`, `no_exact_price`, `no_unique_product`, `no_offer`,
`unsupported_currency`, `ambiguous_price`, `invalid_price`, `price_rule_mismatch`
та технічні `export_error`, `watch_sync_failed`, `duplicate_watches`.
Очікування першого snapshot, блокування магазину або відсутність точної ціни
не роблять завершену синхронізацію невдалою: вони залишаються у звіті, попередня
ціна позначається як така, що потребує перевірки. Неочікувана помилка API або
конфігурації, як і раніше, повертає ненульовий код і позначає systemd service failed.

Telegram успадковується зі спільних налаштувань changedetection.io. За
замовчуванням watch відстежує зміни тексту й JSON-LD цін, тому для галасливих
магазинів варто задати `includeFilters`. Умови «лише зниження» налаштовуються
окремо в changedetection.io. Збої експортера видно в systemd journal; окремі
Telegram-повідомлення експортера не реалізовані.

Стан UUID зберігається приватно поза публічним репозиторієм; на сайті немає
API key, Telegram token або HTML snapshots. Назви watches з префіксом
`OneMoreThing/` зарезервовані для інтеграції — не перейменовуй їх вручну.
Виконані подарунки виключаються автоматично: перед синхронізацією скрипт
читає лише публічні ID завершених записів із `gift_catalog` через той самий
публічний конфіг, що й сайт (`config/catalog-status.json`). Для них власні
активні й архівні монітори видаляються, нові не створюються; статус — `completed`.
Історія цін залишається в репозиторії. Приватні дані власника, примітки та
бронювання не читаються й не змінюються. Якщо публічна перевірка станів
недоступна, синхронізація зупиняється до будь-яких змін моніторів.

Перевірка плану без API-запитів, створення watches або запису даних:

```bash
python3 -B scripts/sync-prices.py --plan
```

Реальна синхронізація (створює/оновлює watches):

```bash
CHANGEDETECTION_API_KEY='<key>' python3 -B scripts/sync-prices.py
```

Перевірки:

```bash
npm test
python3 -B -m unittest discover -s tests -p 'test_*.py'
```

API: [офіційна документація](https://changedetection.io/docs/api_v1/).

### Графік цін і видалення неробочих моніторів

У досьє товару показується SVG-графік із `data/price-history.json`.
Записуються лише реальні успішні перевірки, до 730 точок на товар. Повторний
експорт того самого snapshot не створює дубль. Графік не змішує різні URL,
валюти та ціни з різним статусом ПДВ; для одного запису чесно показується одна
точка. Старих вигаданих цін немає. Початкові точки взяті з уже збережених
успішних `prices.json`.

Перед видаленням моніторів зроби резервну копію datastore. Аудит без змін:

```bash
python3 -B scripts/audit-monitors.py
```

Видалення підтверджено неробочих **власних** моніторів:

```bash
python3 -B scripts/audit-monitors.py --prune
```

Скрипт не видаляє монітори, які ще чекають першого snapshot, чужі монітори
або монітори з неоднозначною відповідністю. При технічному збої API видалення
скасовується. Для видалених джерел зберігається URL і причина в
`config/monitoring-disabled.json`; наступна синхронізація їх не створює знову.
Картки подарунків залишаються. Зміна `originalUrl` автоматично дозволяє нове
джерело; для повторної спроби старого видали відповідний запис із конфігурації.
Закоміть конфігурацію блокування разом зі змінами даних після очищення.

Для сайтів, де JSON-LD містить діапазон варіантів, але Open Graph містить
конкретну показану ціну, профіль може задати `"priceSource": "page_metadata"`.
Так налаштовано UNIQRAINE: береться ціна сторінки, а не мінімум діапазону
інших варіантів. Наявність без окремих однозначних даних лишається невідомою.
Звичайний `Offer` із явним `price` використовує саме це поле, навіть якщо
магазин додатково записує `lowPrice/highPrice`; `AggregateOffer` без профілю
